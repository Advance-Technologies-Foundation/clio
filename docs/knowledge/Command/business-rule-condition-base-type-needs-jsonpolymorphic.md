**What is true** — `BusinessRuleCaseMetadataDto.Condition` is typed as
`BaseBusinessRuleConditionMetadataDto?` so a case can hold either a single
`BusinessRuleConditionMetadataDto` (the shape autogenerated `apply-filter` clear/populate children
need) or a `BusinessRuleGroupConditionMetadataDto`. The `[JsonPolymorphic]` /
`[JsonDerivedType]` attributes on the base class are load-bearing for that, not decoration. No type
discriminator is configured, so the emitted JSON is unchanged in shape - the attributes only make
`System.Text.Json` serialize the runtime type's properties.

**Why it is this way** — `System.Text.Json` serializes a property using its DECLARED type. The moment
a property was widened from the concrete condition to the base class, the derived members stopped
being written unless polymorphism is declared. The same pattern is applied to the action DTO
hierarchy in the same file for the same reason.

**What breaks if you ignore it** — a grouped rule serializes without `logicalOperation` and without
its `conditions` array, and the write still succeeds. The rule reaches Creatio with an empty
condition, so it either never fires or matches everything, and nothing in clio's output hints at the
loss. Any future generalization of a DTO property to a base type in this hierarchy has to add the
`[JsonDerivedType]` entry in the same commit.
