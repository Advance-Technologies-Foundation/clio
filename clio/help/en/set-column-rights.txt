COMMAND TYPE
    Object rights

NAME
    set-column-rights - Set one role's access (denied/read/edit) to one column of one object, move or remove that
    role's row, or turn the object's column permissions on or off (destructive)

SYNOPSIS
    set-column-rights --entity-schema-name <EntitySchemaName> --column <ColumnCode> --grantee <SysAdminUnitId>
        --access <denied|read|edit> [--position <N>] [--enable-column-permissions] [--preview | --confirm] [OPTIONS]
    set-column-rights --entity-schema-name <EntitySchemaName> --column <ColumnCode> --grantee <SysAdminUnitId>
        (--remove-row | --position <N>) [--preview | --confirm] [OPTIONS]
    set-column-rights --entity-schema-name <EntitySchemaName>
        (--enable-column-permissions | --disable-column-permissions) [--preview | --confirm] [OPTIONS]

DESCRIPTION
    Changes the COLUMN (field-level) permissions of ONE object, one column and one grantee per call, through
    RightManagementService SaveAdministratedObject - the payload of the System Designer "Column
    permissions" tab. Read the result with get-column-rights.

    The object is named by its code (entity schema name); a title is refused, naming the code to pass.
    --column is the column's code, resolved to its UId through the entity schema (every package layer
    included). --grantee is a SysAdminUnit id, which must exist.

    How Creatio applies the rows (its "Column permissions" documentation): the higher a row is in a
    column's list, the higher its priority, so a user in several roles gets the access of the highest
    of their rows - this is documented, not measured; positions are reported as the stored order, 0
    first. Users and roles with no row in a column follow the object's operation permissions, and
    object operation and record permissions outrank column permissions. So a column with no rows leaves
    every user to the object's operation permissions. In the designer a role added to a column starts
    with edit.

    --access sets the grantee's row in the column: a grantee with no row gets one at the top (position
    0, which wins), and the other rows move down one; an existing row keeps its place and gets the new
    level. --position N places the row (with --access) or moves the grantee's row (alone) to N, and the
    column's rows are renumbered 0..n-1; when that puts a restriction below an All employees row with
    edit, a warning says the restriction does not apply to members of All employees. --remove-row
    deletes the grantee's row; a removal of a row the grantee no longer has is no change.

    The switch changes only through its flags. A grant while the object's column permissions are OFF is
    refused unless --enable-column-permissions is passed with it; a move or a removal while they are
    OFF is refused (turn them on first). --enable-column-permissions alone turns them on: the rows kept
    on columns since a disable apply again, and every column with no stored row gets the default row -
    run it with --preview first, which names both. --disable-column-permissions alone turns them off and
    keeps every stored row, not applied; it names the columns with no rows, which a later enable
    through clio gives the default row.

    Measured on storage (VwSysEntitySchemaColumnRight): a save with a column list gives each column in
    the list exactly the listed rows and every other column of the object the default row (All
    employees, edit); a save with no list leaves the stored rows alone. So every save that names
    columns is built from STORAGE: every column whose stored rows are not exactly the default, as
    stored, with the named column changed; stored rows of a column that is not in the schema any more
    are sent back as stored. While column permissions are ON, a column with no rows is sent with none,
    so it stays as it is. When the call turns them ON, a column with no rows is not sent, so it gets
    the default row. A column whose last row is removed gets the default row, which widens access (the
    summary says so); removing the only row of a column that has just the default is refused, since the
    default would come back. A disable sends no list.

    Before planning, while column permissions are ON, the stored rows are checked against what the
    service lists (every restricted column with its rows, a column with no rows with none, a default
    column omitted); any disagreement refuses the call, since a save built from a short storage read
    would send the missed columns with no rows, erasing their rows. Storage is counted before it is
    read, and a read with fewer rows than the count is refused. When the call turns column permissions
    on, the service lists nothing to check against, so the rows are read a second time by the object's
    column UIds: rows of this object the first read missed, or rows of the object's own columns stored
    under another schema, refuse the call. The plan's facts, and a refusal or a no-change answer after
    the stored rows were read, say how many stored rows the plan was read from.

    Calls for one object must not run in parallel. Right after the confirmation (never across the
    prompt) a write takes a lease on the object - keyed by the environment's resolved URL and the
    object's code; shared with set-object-rights and set-default-record-rights, among clio processes of
    one OS user (on Windows, of the machine) - and a second write of the object while it is held is
    refused. Then the object and its stored rows are read again; if any of its three switches (column,
    operation, record permissions), its schema UId or a stored row changed since the plan, nothing is
    saved. The save goes out from that fresh read.

    The service answers success whatever it stores, so after every save the switches and the stored
    rows are read back, counted. After a save that names columns, any difference from the plan fails
    the call, and the error says whether nothing was applied or the change was partially applied; a
    changed operation or record switch fails it too. After a disable (no list), a changed stored row is
    only a warning: another client may have changed it.

    The rows are written to the environment only. They are NOT bound to a package: how Creatio carries
    column permissions in a package is not established yet.

OPTIONS
    --entity-schema-name
        The object, by its code. A title is refused, naming the code. Required.

    --column
        Column code whose rows change. Required unless the call only turns the switch.

    --grantee
        SysAdminUnit id (role or user) whose row changes. Required unless the call only turns the switch.

    --access
        denied, read or edit: the level the grantee's row gets. A new row goes to the top (position 0)
        unless --position is given.

    --position
        Position in the column's stored position order, 0 first. With --access it places the row; alone it
        moves the grantee's row. Past the end is refused.

    --remove-row
        Remove the grantee's row; no change when it has none. Removing the column's last row other than
        the default leaves the default row (All employees: edit), which WIDENS access; the summary says
        so. A call of its own: not with --access, --position or a switch flag.

    --enable-column-permissions
        Turn column permissions ON: with --access, or alone. Rows kept on columns since a disable apply
        again, and every column with no stored row gets the default row; run with --preview first.

    --disable-column-permissions
        Turn column permissions OFF, keeping every stored row. A call of its own.

    --preview
        Write nothing: show the change, the column's rows before and after, and whether it would be refused.

    --confirm
        Apply without a prompt (required in a non-interactive run).

    -e, --environment
        Name of the registered environment.

EXIT CODES
    0   The change was saved and the storage read-back matches the plan, the call changed nothing, the
        preview ran, or the prompt was answered no.
    1   An argument was missing, invalid or in a combination that is refused; the object, the column or
        the grantee was not found; several objects have the title; the plan was refused (the switch is
        OFF, a move or removal while OFF, no row of the grantee to move, several rows of it, the
        position is past the end, the removal of a default-only column's row; the read carried no
        readable switch; a stored row has no readable position, level or grantee, so it could not be sent
        back exactly as stored); storage disagrees with the service, is cut short, or cannot be read; the
        schema's columns could not be read; another call holds the object's lease; the stored rows
        changed before the save; the time limit left no room for the save; the save failed; or the
        read-back failed or does not match the plan.

EXAMPLES
    Preview denying a role the Amount column, turning column permissions on:
        clio set-column-rights --entity-schema-name UsrOrder --column UsrAmount --grantee <role-id> --access denied --enable-column-permissions --preview -e dev

    Deny a role the column (a new row goes to the top, position 0, which per the documentation wins):
        clio set-column-rights --entity-schema-name UsrOrder --column UsrAmount --grantee <role-id> --access denied --confirm -e dev

    Let a role read the column, placed second:
        clio set-column-rights --entity-schema-name UsrOrder --column UsrAmount --grantee <role-id> --access read --position 1 --confirm -e dev

    Remove the role's row:
        clio set-column-rights --entity-schema-name UsrOrder --column UsrAmount --grantee <role-id> --remove-row --confirm -e dev

    Turn column permissions off, keeping the rows:
        clio set-column-rights --entity-schema-name UsrOrder --disable-column-permissions --confirm -e dev
