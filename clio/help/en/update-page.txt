COMMAND TYPE
    Development commands

NAME
    update-page - Update the raw schema body of a Freedom UI page

ALIASES
    page-update

DESCRIPTION
    The update-page command validates and saves the raw JavaScript body of a
    Freedom UI page schema. Pass the full body string directly, typically
    after reading raw.body from get-page.
    CLI vs MCP: the CLI get-page verb returns raw.body inline, so the CLI
    caller copies that. The MCP get-page tool returns no raw property - it
    writes the body to disk and reports the path in files.bodyFile. MCP
    callers pass that path straight through as --body-file, or send the
    file contents as --body.

    The MCP update-page tool also accepts validate=false as an explicit escape
    hatch when a full replacement body contains a pre-existing defect unrelated
    to the requested edit. This skips client-side content and run-process
    validation. It does NOT skip the structural floor: JavaScript syntax, AST
    loadability, replace-mode marker integrity, the mobile JSON-object structure
    check, and the page baseline/conflict guard all still run. It can be combined
    with force=true - the flags are orthogonal - and the response then warns that
    both guards are down. The CLI command has no equivalent flag.

    After a successful non-dry-run save, update-page also attempts a
    best-effort live Designer Presence notification so active Creatio
    designers can be warned that the page was saved outside their session.
    This live push requires forms-auth browser-session cookies (login/password
    backed flow). In OAuth-only or credential-less environments the page save
    still succeeds, and the structured response includes a warning when the
    live notification is skipped or fails.

    When the body contains #ResourceString(key)# macros, update-page can
    register missing child-schema localizableStrings before saving. Pass
    --resources when you need explicit captions, or let clio derive captions
    automatically for missing Usr* keys.

    Keep each field control bound to the declared view-model attribute from
    viewModelConfig / viewModelConfigDiff. If validator or handler logic
    is moved to a different attribute for the same field, rebind the
    control to that attribute too.
    If the control is inherited from a parent schema and there is no local
    entry for it in viewConfigDiff, add a local merge for that control
    name instead of editing a non-existent local insert.

    For an own-body field with an undeclared binding, keep the complete insert,
    edit its values, and include its attribute declaration in viewModelConfigDiff
    even when already stored. Append replaces a matching insert as a whole;
    a separate merge does not patch the insert.
    viewModelConfigDiff concatenates entries, so an unchanged declaration is
    appended again with the same effective values. Another append cannot remove it.

    VALIDATION RULES:
    - SCHEMA_CONVERTERS keys (object form) must follow VendorPrefix.Name
      format (e.g., usr.MyConverter).
    - SCHEMA_HANDLERS must be an array of {request, handler} entries; each
      request value must follow VendorPrefix.Name format (e.g.,
      crt.HandleViewModelInitRequest, usr.HandleSomeRequest).
    - SCHEMA_VALIDATORS keys (object form) must follow VendorPrefix.Name
      format (e.g., usr.RequiredValidator).
    - Direct calls from handlers, converters, and validators must resolve to
      a declaration in the page factory scope, a callback parameter, or a known
      JavaScript/Creatio global (MCP update-page / sync-pages / validate-page
      only -- the CLI verb below does NOT run this check). Undefined helper
      calls are rejected before the body is sent to Creatio because Page
      Designer can remove module-scope declarations while preserving handler
      entries, causing ReferenceError.
    MOBILE RULES (MCP update-page / sync-pages / validate-page only --
    the CLI verb below does NOT run them; it checks a mobile body only
    for disallowed sections):
    - Rejected: an operation:"insert"/"set" whose values object carries no
      usable "type" while a "type" sits on the operation object (a type in
      both places is fine when they agree); and a flat "insert" (type
      on the operation object, no values object at all). The Creatio
      differ builds the element from "values" alone, so the type is
      dropped and the element never renders even though the write
      succeeds. A flat "set" is left to the differ, which refuses it for
      the missing required "values".
    - Rejected: a "merge" whose values authors child elements on
      Scaffold's "actions", "leading" or "items" - an array, or a lone
      object, of item configs carrying a non-empty "name". "items" is
      the page body, filled with a MainContainer by every non-blank
      template; the same slot on another container stays advisory. Every shipped FORM
      template populates those slots, so the differ strips the property
      out of the merge and nothing is created even though the write
      succeeds. Put the child in a page container with its own "insert"
      plus a "layoutConfig". clio validates viewConfigDiff against an
      empty base and cannot see the target, so a page built from
      BlankMobilePageTemplate - a bare Scaffold whose slots may be
      empty - is refused too, even though the merge would apply there.
    - Warned: the same authoring in any other slot. There the target may
      legitimately lack the slot, in which case the merge creates it and
      the authoring works; clio validates against an empty base and
      cannot tell the two apart. To author into a slot the target lacks,
      use the two-step idiom: a "merge" creating it as an empty array,
      then one "insert" per child. Both are merge-only: for insert/set
      the values object becomes the element, so children declared there
      are created.
    - Warned: no type anywhere while values carries element properties;
      two DIFFERENT types (the element still renders, as the values
      copy); an operation whose letter case does not match the differ's
      exact-case dispatch; and a crt.Button inserted into parentName
      "Scaffold" / propertyName "actions", which saves but does not show
      up on the mobile designer canvas (ENG-95429) -- place it in a page
      container's "items" with a "layoutConfig" instead.
    - Not enforced: the same type-placement and merge-slot mechanisms
      break web pages too
      and is not checked there; sync-pages validate=false skips these
      checks entirely.
    - User-visible text (label, caption, title, tooltip, placeholder) in
      viewConfigDiff must be a localizable-string binding, not an inline
      literal. Bind via #ResourceString(<Key>)# and register the key's
      default-language value with --resources. Inline literals are rejected.
      Gallery itemConfig.templateValuesMapping values name record attributes
      (e.g. caption: "GalleryDS_Name") and must stay unchanged. Other captions
      still require localization. For a standalone merge, repeat type:
      "crt.Gallery" unless the same body declares that node's type elsewhere.
      Designer-only _designOptions mappings are also excluded.
      A component's own data descriptor is exempt: a "data" object carrying the
      platform's "typeName" marker, on any node that declares a component type
      and at any depth, is component metadata (uId, schemaType, typeName and
      the caption the platform stamped on it), not page-authored text, so a
      literal anywhere inside it is accepted. An input merely named "data"
      (crt.FilterBuilderSource) has no typeName and stays validated. Do not
      delete such a caption to satisfy the rule - the platform never restores
      it.
    - Inserted widget/metric titles must resolve. A title/caption/tooltip/
      placeholder on a freshly inserted (operation:"insert") widget bound as
      $Resources.Strings.<Key> or #ResourceString(<Key>)# is rejected when <Key>
      is not registered via --resources and is not Usr*/DS-bound. A metric title
      #ResourceString(IndicatorWidget_<slug>_title)# is registered only when you
      pass it in --resources; otherwise it renders raw.
    A malformed VendorPrefix.Name causes a Creatio runtime error:
      "Error when register X. Type property should have format VendorPrefix.TypeName"
    - Call `clio get-guidance --name page-schema-converters` for converter details
    - Call `clio get-guidance --name page-schema-handlers` for handler details
    - Call `clio get-guidance --name page-schema-validators` for validator details
    - Call `clio get-guidance --name page-schema-resources` for localization details

    CONFLICT DETECTION:
    update-page guards against overwriting schema changes made outside your
    session (for example, edited in the Creatio designer). It obtains the
    baseline checksum in one of two ways:
      - automatically, from the .clio-pages/{schema-name}/meta.json baseline
        written by a previous get-page for the same environment. No extra flags
        are needed — this is what protects AI-agent CLI flows that read a page
        with get-page and then save it with update-page.
      - explicitly, from --expected-checksum (takes precedence over the on-disk
        baseline).
    Before saving, the baseline is compared against the current
    SysSchema.Checksum of the editable schema. On a mismatch the save is blocked
    with a structured conflict response (conflict: true + conflictDetails)
    instead of silently overwriting the external changes. Re-run get-page,
    re-apply your edit on top of the fresh body, then retry — or pass --force to
    deliberately overwrite. After a successful save the on-disk baseline is
    refreshed automatically, so consecutive updates in the same session do not
    false-conflict. A small race window between the check and the save remains
    (last write wins).

    WRITE MODES:
    --mode replace (default) saves the body verbatim. --mode append loads the
    current schema body from the server and merges your incoming fragment into it.
    A viewConfigDiff entry is replaced only when both operation and name match one
    of yours - and, for a remove or a set, whether it targets properties. Incoming
    wins and keeps the existing entry's position; every other existing operation
    is preserved verbatim, including a second operation on a component you already
    target. One exception: if your fragment supersedes an identity the page
    carries TWICE, only the first is replaced and the later one is dropped, since
    keeping it would re-apply stale values after your replacement. Handlers
    dedupe by request.
    SCHEMA_CONVERTERS and SCHEMA_VALIDATORS entries merge by type key and
    incoming wins. The merged web body is rejected when a custom
    validator reference lacks a matching SCHEMA_VALIDATORS declaration;
    built-in crt.* validators need no local entry.
    Preserved is not the same as applied, and this is not specific to append - it
    is how the platform differ resolves any final body, so a hand-authored
    --mode replace body produces it too. Operations run in whole GROUPS in a fixed
    order (merges, then removes/inserts/moves, set last), never in array order.
    - Warned: a merge, move or element remove sitting beside an insert for the
      same name. It resolves against a base that lacks the component and is
      dropped. Same for a move whose name the body also element-removes; a
      merge whose name the body also element-removes or sets; and a property
      remove whose name the body also sets, or also element-removes unless an
      insert re-creates the element. Fold the values into the insert, or use set,
      which runs after it. Reordering the array changes nothing. The save
      still succeeds; --dry-run reports it too, against the body that would
      actually be written - so in append mode it also catches a pair formed
      between your fragment and the server's body.
      Advisory only: a parent schema inserting the same name can make the
      transform apply after all, and clio cannot see the replacing chain.

    APPEND DRY RUN:
    In append mode --dry-run resolves the current server body, computes the
    merge and returns without saving, reporting the outcome as appendProjection:
    currentOperationCount, incomingOperationCount, projectedOperationCount
    (compare it against the number you expect), addedOperationCount,
    and replacedOperations / replacedOperationCount (replaced in place - not a
    loss). Three DISTINCT loss channels, each with its own fix; two of them warn:
      - droppedOperations: entries from the SERVER body not carried over (the
        further-duplicate exception above). WARNS, one entry per component.
      - viewConfigDiffApplied=false: the current body has no
        SCHEMA_VIEW_CONFIG_DIFF marker pair, so every count describes an array
        the write discards. WARNS; use --mode replace.
      - collapsedIncomingOperations: entries from YOUR OWN fragment that a later
        entry in the same fragment supersedes, since only the last spelling of an
        identity survives. Reported as DATA ONLY, no warning - the fragment is
        yours to read, so warning about your own input would be noise. Counted so
        the totals can be reconciled.
    Named lists are capped; counts are exact.
    Two consequences: an append whose real save could not merge now FAILS the
    dry run with the same error instead of reporting success (that response
    carries dryRun: true, so it stays distinguishable from a failed real save);
    and --mode replace
    is unaffected - it writes verbatim, so there is nothing to project and no
    extra round-trip is made. The same projection is returned on a real append
    save.
    appendProjection speaks for viewConfigDiff only. The sibling *_DIFF arrays
    append unconditionally and cannot lose an entry. Handlers are NOT covered:
    they dedupe by request, and the merge drops every current handler whose
    request appears in your fragment - so a current body carrying one request
    twice keeps neither and your fragment contributes one. Check handlers by
    hand when that shape is possible.
    Append requires the diff form: a full-config body (the SCHEMA_VIEW_MODEL_CONFIG
    / SCHEMA_MODEL_CONFIG markers, instead of the *_DIFF markers) cannot be merged
    and is rejected with an actionable hint — use --mode replace for such a body.
    The message names which body is full-config: convert your own incoming body to
    the diff form, but if the current page on the server is full-config (every
    create-app-section page is), append is not supported against it — use
    --mode replace.

SYNOPSIS
    clio update-page [options]

OPTIONS
    --schema-name                      Page schema name to update

    --body                             Full raw JavaScript schema body (a
                                       string with /**MARKER*/ pairs, not a
                                       structured object)

    --body-file                        Path to a file containing the body.
                                       Alternative to --body for large bodies

    --mode                             Write mode: 'replace' (default) or
                                       'append' (merge with the current body).
                                       Append requires the diff form; a full-
                                       config body is rejected — use 'replace'

    --dry-run                          Validate only and do not save

    --resources                        Valid JSON object of resource key-value
                                       pairs for #ResourceString(key)# macros
                                       Malformed JSON is rejected during
                                       validation

    --optional-properties              JSON array of {key, value} objects to
                                       merge into schema optionalProperties,
                                       e.g. '[{"key":"entitySchemaName",
                                       "value":"UsrMyEntity"}]'

    --expected-checksum                Baseline SysSchema checksum of the
                                       editable schema (from get-page). Blocks
                                       the save with a conflict error when the
                                       server-side checksum differs

    --force                            Skip the external-modification check
                                       and deliberately overwrite out-of-band
                                       changes

    --uri                    -u       Application uri

    --Password               -p       User password

    --Login                  -l       User login (administrator permission required)

    --Environment            -e       Environment name

    --Maintainer             -m       Maintainer name

EXAMPLE
    clio update-page --schema-name UsrTodo_FormPage --body "<raw body>" --dry-run true -e dev
        validate a raw Freedom UI body without saving it

    clio update-page --schema-name UsrTodo_FormPage --body "<edited raw body>" -e dev
        save the edited raw Freedom UI body to the registered dev environment

    clio update-page --schema-name UsrTodo_FormPage --body "<edited raw body>" --resources "{\"UsrDetailsTab_caption\":\"Details\"}" -e dev
        save the page and register the missing child-schema localizable string

    clio update-page --schema-name UsrTodo_FormPage --body "<edited raw body>" --optional-properties "[{\"key\":\"entitySchemaName\",\"value\":\"UsrTodo\"}]" -e dev
        save the page and merge custom optional properties into the schema
