COMMAND TYPE
    Object rights

NAME
    set-object-rights - Grant or revoke object operation permissions (read/create/edit/delete) for a role on an object

SYNOPSIS
    set-object-rights --entity-schema-name <EntitySchemaName> --grantee <SysAdminUnitId> [--operations read,create,edit,delete] [--revoke] [--disable-operation-permissions] [--include-connected] [--connected-operations read,...] [--allow-security-object] [--confirm | --preview | --confirmation-code <code>] [OPTIONS]

DESCRIPTION
    Grants (or, with --revoke, revokes) object operation permissions for one role on an object — the
    SysSchemaOperationRight / "Object permissions" layer that decides who may read/create/edit/delete
    ANY record of an entity. This is the object-level analog of set-record-rights (which is per-record),
    and it works for any role.

    It is a read-modify-write over the native RightManagementService: the object's per-role grid is
    read, the grantee's row is added/updated (or removed), and the object is saved. Granting to an
    object that does not yet use operation permissions turns them on — an access narrowing for every
    other role, which the confirmation and the result line both name. So internal users keep access,
    the same save adds an "All employees" row with read/create/edit/delete when the object has none
    (Creatio 8.3.4 adds it on its own too); an existing All employees row is left as it is. For
    exclusive access, revoke or narrow that row afterwards. It does NOT change column permissions.

    A revoke only ever narrows access. Removing an object's LAST rights row is the one case that would
    not: it turns operation permissions off, which makes the object available to ALL internal users. That
    is refused unless --disable-operation-permissions asks for it explicitly.

    DESTRUCTIVE: this command changes access. In a non-interactive run it refuses to apply unless
    --confirm is passed; in an interactive run it asks for a y/n confirmation. --preview, --confirm and
    --confirmation-code are mutually exclusive; a matching --confirmation-code replaces the prompt.

    The object name is trimmed and must be a plain schema identifier (letters, digits, '_').

OPTIONS
    --entity-schema-name
        Object (entity schema) name whose operation permissions are changed (for example UsrOrder). Required.

    --grantee
        SysAdminUnit id (organizational/functional role or user) to grant or revoke. Names are not
        unique, so the id is required. Resolve it yourself (e.g. execute-esq on SysAdminUnit).

    --operations
        Comma-separated operations to grant/revoke: read, create, edit, delete. Default: read, create, edit (delete not granted by default).

    --revoke
        Revoke the operations instead of granting them. A role left with no operations is removed.

    --disable-operation-permissions
        Allow a revoke to remove the object's LAST rights row. Doing so turns the object's operation
        permissions OFF, which makes it available to ALL internal users — an access widening, so it
        never happens implicitly. Without this flag such a revoke changes nothing and exits 1. It
        applies to the root object only, never to connected lookups.

    --include-connected
        Also apply to every object referenced by the root object's OWN lookup columns.
        The connected lookups get --connected-operations (read only by default), NOT --operations.
        Security and system objects (SysAdmin*, SysUser*, SysSchema*, SysPackage*, SysSettings*, SysLic*, SysProcess*, Vw*,
        *Right/*Rights) are skipped with a warning; name one as --entity-schema-name to change it.
        With --revoke the lookups are left untouched unless --connected-operations is given. If the
        lookups cannot be enumerated, nothing is written and the command exits 1.

    --connected-operations
        Operations applied to the connected lookup objects with --include-connected. Default on a grant:
        read — picking a lookup value only needs read, so create/edit are never fanned out to shared
        dictionaries (status/type lookups, Currency, Contact, Account) unless passed here explicitly.
        On a revoke there is no default: without this option the lookups are not changed.

    --allow-security-object
        Allow granting create/edit/delete, or a revoke with --disable-operation-permissions, when the
        ROOT object is a security or system object (SysAdmin*, SysUser*, SysSchema*, SysPackage*,
        SysSettings*, SysLic*, SysProcess*, Vw*, *Right/*Rights). Without it such a root may only be
        granted read. A plain revoke on such a root is allowed.

    --confirm
        Confirm the destructive change without a prompt. Required in non-interactive runs.

    --preview
        Write nothing: list every object the call would change, its current state (including which
        other roles hold rights) and what it would get, and print a confirmation-code. A root that
        cannot be read or does not exist fails the preview and no code is issued.

    --confirmation-code
        Apply the change only if the arguments, the targets and every role's rights on them are still
        exactly what the preview with that code showed; otherwise refuse and change nothing. On MCP a
        call without confirm is a preview, and confirm=true requires this code. The code is a state
        fingerprint, not a secret.

    -e, --environment
        Name of the registered environment to change.

EXIT CODES
    0   The change was applied (or was already in the requested state, or cancelled at the prompt), or a
        --preview completed (nothing was written).
    1   An input was invalid (missing or non-identifier entity-schema-name, grantee not a GUID, unknown
        operation, --preview/--confirm/--confirmation-code combined),
        confirmation was missing in a non-interactive run, the named (root) object was not found, the
        connected objects could not be enumerated, a write failed, or a revoke was refused because it
        would have removed the object's last rights row, the grantee does not exist, a grant beyond read
        targeted a security/system root without --allow-security-object, a revoke with
        --disable-operation-permissions targeted a security/system root without it, a preview could not
        read the root, the confirmation code did not match, or turning operation permissions on left All
        employees without read (the change is saved). When the root change did not happen the connected
        objects are not attempted. A connected lookup that is not found only warns.

EXAMPLES
    Make an object and its lookups readable by a role (lookups get read only):
        clio set-object-rights --entity-schema-name UsrOrder --grantee <role-id> --operations read --include-connected --confirm -e production

    Grant a functional role the default read/create/edit on one object:
        clio set-object-rights --entity-schema-name UsrOrder --grantee <role-id> --confirm -e production

    Grant a functional role full access, including delete:
        clio set-object-rights --entity-schema-name UsrOrder --grantee <role-id> --operations read,create,edit,delete --confirm -e production

    Revoke delete from a role:
        clio set-object-rights --entity-schema-name UsrOrder --grantee <role-id> --operations delete --revoke --confirm -e production

    Return an object to "available to all internal users" by removing its last role grant:
        clio set-object-rights --entity-schema-name UsrOrder --grantee <role-id> --operations read,create,edit,delete --revoke --disable-operation-permissions --confirm -e production

NOTES
    The grantee must exist in SysAdminUnit; an unknown id fails before anything is written.

    When a grant turns operation permissions ON, the object is read back and the result names the roles
    that hold rights afterwards. If All employees holds no read afterwards, the command fails (exit 1):
    internal users outside the listed roles lost access, and the change is already saved. Granting All
    employees itself is not such a failure. With --include-connected a call can take minutes.

    Read-modify-write is last-writer-wins: a change another client saves between the read and the save
    is overwritten. Read the result back with get-object-rights when concurrent edits are possible.
