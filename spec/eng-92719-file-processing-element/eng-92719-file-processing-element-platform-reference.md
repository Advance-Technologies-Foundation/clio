# Platform reference: ENG-92719 File processing element and ENG-95984 File process parameter type

**Summary.** This document describes what the Creatio platform already does, end to end, for the "Process file"
element and for file-typed process parameters. It is the background for ENG-92719 File processing element (sub-tasks
ENG-96505 Element readiness and object attachments mode and ENG-96506 Generated report + process parameter modes) and
for ENG-95984 File process parameter type, all in epic ENG-92704 Create BP via AI Toolkit. "Process file" is not one
element: it is **three user-task schemas that share one caption**, and the designer's "What is the source of the
file?" choice selects the schema; it is not a parameter. A file always travels through a process as a **reference**
(`IFileLocator`, data value type FileLocator), never as bytes. Every file output, and the one file input, is the
generic "Collection of records" type with one nested FileLocator item. The server runtime decides nothing on its own: it
honours whatever parameter values it is given and validates almost none of them. So most configuration mistakes are
**silent**: files saved onto no record or onto the wrong one, 50 arbitrary files read, one Word document per record of
a whole entity. The classic designer supplies the rules the server does not enforce: attachment storage chosen per
entity, `ResultActionType` defaults, and `Files` bound at two levels. The diagram needs only
`ManagerItemUId = SchemaUId`, a 69x55 size and a lane. Every runtime statement is a source trace (a hypothesis)
unless it is marked *measured*; section 13 lists the stand measurements that turn the load-bearing ones into facts.

### 2.2 The source is the schema

"What is the source of the file?" offers Object attachments, Generated report and Process parameter. These are
client-only constants, `ReadFiles "0"`, `GenerateReports "1"` and `UseProcessParameter "2"`
(`PD/ProcessUserTaskConstants/ProcessUserTaskConstants.js:176-180`). `_getUserTaskName` maps them to the three schema
names (`PD/BaseFileProcessingUserTaskPropertiesPage/BaseFileProcessingUserTaskPropertiesPage.js:242-253`). **No schema
declares a source parameter.** Changing the source replaces the element (§8.3). The palette offers only one entry,
"Process file", and it creates ObjectFileProcessingUserTask (§9.3).

## 5. Runtime algorithms

### 5.1 What all three variants share (source)

- **Synchronous.** Each overrides `InternalExecute(ProcessExecutingContext)` and returns `true`. None waits for a user,
  and none has a validation hook. An exception that escapes fails the element.
- **Every element parameter is read before `InternalExecute` runs.** The read loop has no `HasValue` gate
  (`CORE/Terrasoft.Core/Process/ProcessFlowElement.cs:577-590`). A process saved with `IsInterpretable = true` runs in
  flow-engine mode (`CORE/Terrasoft.Core/Process/ProcessComponentSet.cs:139`), and CrtProcessBuilder saves processes
  that way (`PB/Design/ProcessBuildHandler.cs:401`).
- **Rights.** Reads use the running user's rights: `UseAdminRights = false` (`PD/FileProcessing/FileProcessing.cs:145`;
  `GEN/ReportEngine.Reports.cs:166-168`). Writes go through a factory `WithRightsDisabled()`
  (`FileProcessing.cs:157`; `ProcessFileProcessingUserTask.cs:27-30`; `ReportFileProcessingUserTask.cs:44-47`). Net
  effect: a file the user cannot read is not found, and a file is written regardless of rights on the target.
- **New file rows** get `Version = 1` (`FileProcessing.cs:199`) and `Type = File`
  (`CORE/Terrasoft.File/Metadata/EntityFileMetadataStorage.cs:199-200`).

### 5.2 Object attachments (`ObjectFileProcessingUserTask.cs:94-112`)

1. `sourceSchema = GetInstanceByUId(SourceEntitySchemaUId)` (`:96`). This throws on an empty or unknown UId.
2. `esq = new EntitySchemaQuery(sourceSchema) { RowCount = RecordsToRead }` (`:98-100`).
3. `SpecifyESQFilters(…, DataSourceFilters)` (`:101`). An empty string means no filter. The DataContract format is
   detected by `"className":"Terrasoft.FilterGroup"`, and the legacy `DataSourceFilterCollection` JSON is also accepted.
   Leaf columns resolve on **`esq`'s root**; the `rootSchemaName` stored inside the JSON is ignored
   (`CORE/Terrasoft.Nui.ServiceModel/Extensions/QueryExtension.cs:957-962`, `:640-642`).
4. `SpecifyESQOrderByStatement(esq, OrderByInfo)` (`:102`). The format is `Column:Direction:Position[,…]`, with
   direction 1 = ascending and 2 = descending. An entry that is not three parts is **skipped silently**. A column the
   root lacks throws `ItemNotFoundException`.
5. `FillFileDataFilters` (`:36-47`) **always** adds `Type = FileConsts.FileTypeUId`, so link-type attachments are
   never read. When `SourceDataEntitySchemaUId` is set it also adds `RecordSchemaName = <that schema's Name>`.
6. Branch (`:104-110`):
   - **0 SaveToFiles**: `CopyFiles` (`:77-87`) → `FileProcessing.CopyUseFileFactory` (`FileProcessing.cs:152-179`).
     The target schema is resolved first (throws if empty). The link column is `FindByUId(ConnectedObjectColumnUId)`,
     and null is tolerated. For each source file it creates `EntityFileLocator(target.Name, NewGuid)`, sets the link
     column to `ConnectedObjectId` (only if the column was found), `Version = 1`, `RecordSchemaName` (only if
     `TargetDataEntitySchemaUId` resolves), then `sourceFile.Copy(targetFile)`. Outputs: `ObjectFiles` = the
     **SOURCE** locators, and `CreatedObjectFileIds` = the copies' Ids.
   - **1 UseInProcess**: `ReadFiles` (`:71-75`). `ObjectFiles` = locators of the EXISTING attachment rows, and
     `CreatedObjectFileIds` = an empty list. Nothing is copied, and the locators outlive the process.
   - **anything else**: `NotSupportedException` (`:108-109`; pinned by `UT/ProcessDesigner.UnitTests/ObjectFileProcessingUserTask_Tests.cs:188-200`).
7. Reading (`FileProcessing.cs:144-150`, `:209-224`): `CanReadUncommitedData = true`, `IgnoreDisplayValues = true`, a
   raw select that reads only `Id`; the locator schema is `esq.RootSchema.Name`.

### 5.3 Process parameter (`ProcessFileProcessingUserTask.cs:68-97`)

1. `ResultActionType` must be 0. Any other value, 1 included, throws `NotSupportedException` before `Files` is
   iterated (`:89-97`; pinned by `UT/ProcessDesigner.UnitTests/ProcessFileProcessingUserTask_Tests.cs:103-112`).
2. `SaveEntityFiles` (`:68-82`) resets `CreatedObjectFileIds`, then resolves the target schema **first**
   (`GetEntityFileFactory`, `:47-66`). So an empty or unknown `TargetEntitySchemaUId` throws even when `Files` is empty.
3. `foreach` row of `Files`: `row.TryGetValue("File", out IFileLocator src)` (`:73`).
   - Key absent: the row is skipped **silently**.
   - Key present with a null value: `UserConnection.GetFile(null)` → `FileFactory.CreateFileInstance` →
     `fileLocator.GetType()` → **NullReferenceException** (`CORE/Terrasoft.File/FileFactory.cs:45`).
   - A value of another type: **InvalidCastException** (`CompositeObject.cs:120-127`).
4. Copy: `targetFile.Name = sourceFile.Name` (`:76`; this loads the source, so a missing source row throws
   `FileNotFoundByLocatorException`), then `sourceFile.Copy(targetFile)` (`:77`).
5. Output: `ObjectFiles` rows `{"ObjectFile": <TARGET locator>}`. This variant outputs the COPIES; the Object variant
   outputs the ORIGINALS.

Any `IFileLocator` is a valid source: an attachment row, a `SysProcessFile` temporary file from a Report element, and so
on. How `Files` is filled from its bindings is in §6.4.

### 5.4 Generated report (`ReportFileProcessingUserTask.cs:182-193`)

1. `filters = GetInitializedFilters(Owner, DataSourceFilters)` → `ProcessFilterFactory.Create`
   (`CORE/Terrasoft.Nui.ServiceModel/DataContract/ProcessFilterFactory.cs:202-209`). An empty string gives
   `new Filters()`, which means **no condition**. Only the DataContract format is accepted. Right-hand parameter
   mappings are resolved from the process.
2. `ReportEngine.Generate(new ReportSettings {Id = ReportId, Filters, IsSeparateReports})` (`:184-189`). `Generate`
   is eager: it reads the report row and switches on the type (`GEN/ReportEngine.Reports.cs:304-317`). The per-type
   generators are lazy iterators.
3. The factory is chosen by `ResultActionType` (`:98-112`): 0 → entity files of the target (same mechanics as §5.3
   step 2); 1 → `CreateTempFile` (§5.6); any other value throws `NotSupportedException` after `Generate` has returned
   and before the first file.
4. For each report: name it (§5.4.2), then `reportFile.Write(report.Data)` (`:60-64`, `:141-154`).
5. Outputs: `ReportFiles` rows `{"File": locator}`; `CreatedObjectFileIds` filled only for 0.

#### 5.4.2 File name formula (source; pinned by `UT/ProcessDesigner.UnitTests/ReportFileProcessingUserTask_Tests.cs:214-319`)

```
caption = SysModuleReport.Caption            // localizable: read in the process RUNNER's culture
prefix  = (ReportName non-empty AND ReportNameDataSourceColumnUId empty) ? caption + ". " + ReportName : caption
name    = IsSeparateReports
            ? prefix + ((column set AND its value non-empty) ? ". " + value : " (" + i + ")")
```

Lines: `ReportFileProcessingUserTask.cs:53-58`, `:156-175`. `ReportName` is always a suffix, never the whole name, and it
is ignored when a name column is set. `i` is the 1-based enumeration index; record order is unspecified, so the

because the reader looks it up by its column name, not its value alias. A mid-run failure leaves the files already
written in place: the task has no transaction (hypothesis).

### 5.7 Copy semantics (source, `CORE/Terrasoft.File`)

`IFile.Copy` → `File.CopyAsync` (`File.cs:254-262`) → `CopyProperties` (`:182-187`): the target's `Name` is set only
when blank, then `CopyAttributes` (`:174-180`) copies **every source attribute the target has not already set**. The
source's attributes are all its loaded columns except `Id`, `Name`, `Size`, `TotalSize`, `CreatedOn`, `ModifiedOn`,
`TypeId`, `SysFileStorageId` and `Data` (`Metadata/EntityFileMetadataStorage.cs:29-39`, `:115-125`). An attribute with
no matching column on the target is logged at WARN and dropped (`:159-164`).

| Situation | Result | Silent? |
|---|---|---|
| Legacy copy, e.g. ContactFile → ContactFile, valid link column and id | linked to `ConnectedObjectId`; `Notes`, `Tag`, `FileGroup`, `LockedBy`/`LockedOn` inherited from the source | yes (inheriting a lock is surprising) |
| **Same-schema copy, `ConnectedObjectColumnUId` missing or wrong** | the target never sets the link, so it inherits the SOURCE's link: a duplicate on the **source** record | yes |
| Cross-schema copy (ContactFile → AccountFile), column missing | the source link has no column on the target and is dropped: linked to **no record** | yes |
| SysFile target, `TargetDataEntitySchemaUId` empty, SysFile source | `RecordId` set, `RecordSchemaName` **inherited from the source** | yes |
| SysFile target, `TargetDataEntitySchemaUId` empty, legacy source | no `RecordSchemaName` at all | yes |
| SysFile target with `TargetDataEntitySchemaUId` set (what the designer always writes) | `RecordId` and `RecordSchemaName` stamped by the target | no |
| `ConnectedObjectId` = `Guid.Empty` on a legacy target | written as `00000000-…`, not NULL. The non-weak lookup has a DB foreign key, so the predicted result is a FOREIGN KEY violation and the element fails | no (loud) |
| `ConnectedObjectId` = `Guid.Empty` on a SysFile target | `RecordId` is a plain Guid with no FK: saved as an **orphan** | yes |
| `TypeId` of every copy | always File, even when the source is a link | yes |

`UseEntityFileApi` (on by default) changes only `Delete`; copies save through `SaveToDb` and are unaffected
(`EntityFileMetadataStorage.cs:296`, `:314-321`). A copy within one content storage is done server side; otherwise
the content is streamed (`File.cs:224-231`, `:196-200`). The empty-`ConnectedObjectId` outcomes are pending M17; it
starts with a read-only FK pre-check.

Pending **M1**; no shipped process has it |

Notes, all basis = source:

- The one-row path is `TryGetListValue`. The flag `HasCollectionWithOneElement`
  (`BaseFlowSchemaGenerator.cs:466-489`) is unrelated: it only feeds the multi-instance iteration count
  (`ProcessInstanceCollectionParametersDataReader.cs:64-71`).
- An ordinary user task DOES read a nested-only `Files`. `HasValue()` gates only generated process-parameter reads
  (`ProcessSchemaGeneratorNew.cs:3149-3164`), not element parameters. The provenance filter that hides a nested-only
  binding exists only on the sub-process start path (`ProcessParameterValueProvider.cs:718-753`, called from
  `ProcessComponentSet.cs:1361-1366` and `:1518-1521`); an ordinary element is initialised from all its parameters
  (`ProcessComponentSet.cs:502-540`). The source trace therefore favours a one-row read, but the claim stays disputed
  until **M1**. The same range holds a restore-path overload, `InitializeFlowElementProperties(..., useOnlySchemaValues)`
  (`:531-540`, reached from `TryCreateProcessElement`, `:1272`), which keeps only None/ConstValue parameters that have a
  value; the trace has not ruled that path out.
- A **stale value** is possible in one corner: the reader prefers a stored value at the element's own `Files` path
  (`:578-580`). That value is stored only when another element maps FROM `Files`, and it matters only when the element
  runs again in a loop. The platform rule below forbids such a mapping anyway.
- `ParameterValuesValidationRule`, behind `FeatureUseVerificationOfProcessParameterDirection` (default true,
  `CORE/Terrasoft.Core/GlobalAppSettings.cs:359`), refuses a mapping that READS an `In` parameter of another element,
  so `Files` cannot be used as a source (`CORE83/Terrasoft.Core/Process/ParameterValuesValidationRule.cs:252-286`).

### 6.5 The value at run time and where it is stored

- A file value is an **`IFileLocator`** object, a marker interface over `ISerializableObject`
  (`CORE/Terrasoft.File.Abstractions/IFileLocator.cs`). The three tasks only produce `EntityFileLocator`, whose
  schema is the FILE object. Its JSON form, inferred from the writer code and not captured from a stand, is
  `{"v":{"t":"Terrasoft.File.EntityFileLocator, Terrasoft.File","v":{"_entitySchemaName":"ContactFile","_recordId":"…"}}}`.
- A file collection value is a `CompositeObjectList<CompositeObject>`; each row is a string-keyed dictionary.
- Storage in a running process: `ISerializableObject` values (every locator and every collection) are serialized to
  JSON (`FlowEngineStateService.cs:409-428`). A collection of fewer than 100 rows is stored inline in the parameter
  value; 100 rows or more go to `SysPrcCollectionStore` in chunks of 400 while `FeatureUseOptimizedCollectionStore` is
  on (threshold: `CORE/Terrasoft.Core/Process/ObsoleteProcessCollectionStore.cs:54, 95`; chunk size:
  `CORE/Terrasoft.Core/Process/CollectionStoreDBProvider.cs:65`; default true: `GlobalAppSettings.cs:853`). Reads
  handle both forms transparently.
- The legacy compiled process generator has no branch for FileLocator. A process-level single File therefore relies on
  the flow-engine store, which interpreted processes always use (`CORE83/Terrasoft.Core/Process/ProcessGenerator.cs:70-120`;
  medium confidence).

### 6.6 Which types a process parameter may have

There is **no server-side allow-list**. `DataValueTypeManager` registers every type, and
`GetProcessSchemaParameterDataValueTypes` is named by a values provider but implemented nowhere in core or the
corpus (`CORE83/Terrasoft.Core/DataValueTypeManager.cs:754-778`). `ParameterValuesValidationRule` checks expression and
mapping type compatibility, not membership: a mapping must have `fromType == toType` or an implicit cast, so a
FileLocator target accepts only a FileLocator source (`ParameterValuesValidationRule.cs:288-307`). What the designer
offers is in §8.6.

### 7.3 The designer's per-entity rule

With `ProcessFeatures.UseSysFileInObjectFileProcessing` ON (§10), `getFileEntities` takes the SysFile-aware path
(`PD/EntitySchemaDesignerUtilities/EntitySchemaDesignerUtilities.js:509-515` → `_getFileEntities` `:412-458`):

1. Take every base (non-replacement) entity, intersected with `SchemaDataDesignerService.GetAvailableEntitySchemas`
   (non-virtual, non-view; **when that service call fails, nothing is filtered**, `:295-309`). Drop entities whose
   direct parent is BaseEntityInTag, BaseFolder, BaseItemInFolder or BaseTag (`:330-338`, `:402-407`).
2. **File objects** are BaseFile descendants that are neither BaseFile itself nor in the SysFile family (SysFile and
   its descendants such as FeedFile) (`:314-325`).
3. Each file object is paired with a record entity **by name**: strip the `File` suffix; `FileLead` pairs with `Lead`
   (`:424-446`). A file object whose name does not resolve to an entity is listed on its own (an orphan, e.g.
   DNSGuideFile, CreatioAIIntentFile, MailboxSettingsFile).
4. A paired file object becomes one entry captioned **"`<Entity>` (`<file object caption>`)"**, with
   `isFileSuccessor: true` (`:343-358`).
5. **Every other** eligible entity that no file object claims becomes a SysFile entry with its plain caption,
   `fileEntitySchemaUId = SysFile`, `isFileSuccessor: false` (`:363-387`). SysFile itself and FeedFile land here too,
   as degenerate entries.
6. The link column is `SysFile.RecordId` for a SysFile entry (`PD/BaseFileProcessingUserTaskPropertiesPage/…js:527-540`).
   Otherwise it is the column of the file object whose `referenceSchemaUId` is the record entity **and** whose name
   equals the entity name (`EntitySchemaDesignerUtilities.js:526-549`). When there is none, the link column is left
   unset and the files are saved unlinked; GenerateDNSRecordsSpecification shows this shape for its orphan DNSGuideFile
   target (corpus).
7. Writes: `*EntitySchemaUId = fileEntitySchemaUId` and `*DataEntitySchemaUId = entity` for both kinds; the data UId is
   **cleared on save** for a file-object entry (`BaseFile…js:421-436`, `:841-849`; Object source side
   `ObjectFileProcessingUserTaskPropertiesPage.js:184-202`, `:319-328`).

So with the flag ON, an entity that has its own `<X>File` keeps the legacy encoding; only entities without one use
SysFile. With the flag OFF, the list holds only `<Section>File` objects from `ModuleStructure` (plus FileLead), and
dedicated-storage output is byte-identical in both modes (`:250-290`). A SysFile-mode element still RUNS with the flag
OFF; the designer then shows an empty object field and cannot re-save it without reconfiguring
(`BaseFile…js:657-670`, `:866-877`). In the 10.1.37 configuration, 37 file objects pair this way, 8 are orphans, 2 pair
with a DB view and 2 are in the SysFile family (scan of `GEN`). Every paired object has the designer-conforming link
column.
