## Acceptance Criteria

- [x] **AC-01** — `IEntityConnectionCatalog` / `EntityConnectionCatalog` reads `EntityConnection` for a
  **host entity supplied as a constructor input, defaulting to `Activity`** (D2), resolved through
  `EntitySchemaResolver.ResolveByName` and kept as a *named* default — not an inline literal. It resolves
  each `ColumnUId` and returns `{ Name, Caption, DataValueTypeUId, ReferenceSchemaUId }`.
- [x] **AC-02** — The candidate set is *registry ∪ element parameters ∩ host `Columns`*, computed **per
  element**. A global catalog that would accept `Application` on a Send email is a defect: the static
  parameter sets differ per user task.
- [x] **AC-03** — The catalog reads the registry **with admin rights** (or via a plain `Select`). It must
  **not** copy the designer's `UseAdminRights = false` ESQ: the caller has already passed
  `CanManageProcessDesign` and the registry carries no user data. Failure mode being avoided is an empty
  candidate list that presents as a validation bug.
- [x] **AC-04** — The tag, wherever one is produced, is **derived** as `$"{host.Name}Connection"`. The
  literal `"ActivityConnection"` must not appear in the source — `Activity` has a column of exactly that
  name, so a literal invites a tag/column self-reference confusion.
- [x] **AC-05** — `ConnectionCapability` holds the **explicit allow-list keyed on user-task schema
  Name/UId**, applied on write paths only, and refuses anything unlisted while naming the schema.
- [x] **AC-06** — `ConnectionCapability` also owns the **effectiveness rule** (D3): `ActivityUserTask` →
  always; `EmailTemplateUserTask` → `CreateActivity == true` **or** manual send mode;
  `AutoGeneratedPage` / `PreconfiguredPage` / `UserQuestion` / `OpenEditPage` → `CreateActivity == true`.
  Manual-send email must evaluate **effective**, because `ManualEmailUserTaskSender.cs:56-69` has no gate.
- [x] **AC-07** — `UserTaskDeprecationPolicy` implements `usageType == None ∥ name ∈ {SendEmailUserTask,
  EmailUserTask}` and resolves the user-task schema as `FindInstanceByUId(uid) ??
  FindInstanceFromMetaData(uid)`. A test must prove the metadata fallback is exercised — without it the
  predicate silently returns `Advanced` for everything and `CallUserTask` passes.
- [x] **AC-08** — The deprecation policy lives **outside** `ConnectionCapability` and is not consulted by
  any connections refusal (D9 scope). Its ONLY consumer is `describe`'s `deprecated` flag. The
  build/`addElement` policy refusal that D9 also envisaged was **not implemented** — nothing in the package
  refuses a retired user task, so `addElement` with `SendEmailUserTask` succeeds. Recorded in the plan's D9
  entry and §3.6 rather than left as an implied promise; the flag is reporting only.
- [x] **AC-09** — Unit tests cover all of the above. **No test asserts caption content**: the fixture's
  `CreateLookupColumn` sets `Caption = new LocalizableString()` (empty).

## Deviations recorded at implementation time

Three, each forced by a fact that only surfaced against the platform assemblies:

1. **AC-07's seam does not exist as named.** `FindInstanceFromMetaData(Guid)` is `internal virtual` on
   `SchemaManager<T>`, so a configuration package cannot call it — the shipped site the ADR cites is inside
   `Terrasoft.Core`. The implementation uses the public equivalent `FindRuntimeSchemaFromMetaData(Guid)`,
   which deserializes the same stored metadata hierarchy (so `UsageType` IS populated, which is the point of
   the fallback). Two consequences worth carrying forward: it returns `null` for an unknown UId and throws
   only for an extend-parent (package-layer) UId — the opposite of what was assumed; and it is the platform's
   **uncached** variant and re-initializes the schema's resource manager on each call, which is why the
   policy memoizes verdicts per request. A cheaper public seam to measure later is the manager's metadata
   *item* read, which is what the internal cached method calls underneath.
2. **The `ProcessObsoletedElements` flag is not honoured** (D9's residual). The server-side feature-read
   extension is not in the reference assemblies used for the local build and the feature code cannot be
   verified from available sources; a wrong code reads as "disabled" forever, which is the silent-failure
   class this feature exists to remove. **Correction (recorded during the final review):** the effect is the
   OPPOSITE way round from what this deviation first said. The predicate refuses nothing, so not honouring the
   flag cannot make the package stricter about authoring — it only means a `deprecated: true` label where a
   flag-enabled environment would say false. Reading is what differs; authoring is unaffected either way. The
   ADR still recommends honouring the flag; nobody has needed to yet, and the label is the whole exposure.
3. **AC-06's rule is stricter than the platform for two of the four page tasks.** `UserQuestionUserTask` and
   `OpenEditPageUserTask` gate on `CreateActivity || !(Owner is ProcessComponentSet)`, so inside an ordinary
   business process — all this package builds — they create the activity regardless of `CreateActivity`. The
   rule as specified is implemented anyway: over-refusing costs one array element and the suggested fix is
   harmless there, whereas under-refusing reopens the silent-inert case. Flagged for the reporter; one row of
   a table to change if they decide otherwise.

A fourth item is out of scope and was spun out: the package's DI root is built without `ValidateScopes`, so a
scoped collaborator resolved from the public root accessors would capture one request's `UserConnection` for
the process lifetime. Pre-existing, wider blast radius than this story.
