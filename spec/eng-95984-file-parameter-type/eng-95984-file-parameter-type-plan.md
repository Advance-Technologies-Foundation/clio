## 0. Summary

Admit a file as a process parameter **by reference, never by bytes**: `File` is the platform's FileLocator type
(`A33C9252-D401-453E-949D-169157067ED9`, one file) and `FileCollection` is the generic record collection
`CompositeObjectList` (`651ec16f`) with exactly one FileLocator item named `File` (several files). The ticket's
wording does not survive the source: Binary is a Stream type the flow engine cannot store, the platform type NAME
`"File"` resolves to a different BLOB type, one declared type cannot be both a single file and a collection, and the
element outputs exist for both values of `ResultActionType`, not only for 1. Admitting the type is the small half
(about two hours of code). The real work is the binding: the runtime rebuilds a collection's rows from the TARGET's
own items, so a file collection bound only at its outer level saves green and fails at run time (source), while
shipped content binds both levels in 11 of 11 file-collection bindings (measured, corpus). ENG-95984 File process parameter type therefore also
teaches the shared mapping funnel `ProcessMappingService.ApplyMapping` (used by `mappings[]`, `addMapping`, the
mirror, `setConnections` and approvals) to bind both levels and to refuse the shapes
that crash, adds dotted process-parameter paths, and makes describe read back what it wrote. That changes what an
existing operation writes in every process (an item-only multi-instance mapping now also binds its collection), so
the clio `[RequiresPackage]` floor moves and two shipped guidance passages are rewritten under a version gate.
Delivery is one feature PR per repository (CrtProcessBuilder, then clio, then clio-knowledge). Before them comes a
docs-only clio PR with this ticket's BMAD set, which must merge before the package PR opens (section 10). Stand
measurement M3 refuted the suspected ENG-96230 Collection process parameter type mirror defect (H-1) on 2026-10-02,
so no extra triple is added: binding the mirror's items is one parity commit in the package PR. With an AI agent writing the code, it takes about 7-15 h of agent time and 4.5-10 h of the owner's time; calendar about 3-5 working days from day 0. It blocks ENG-96506 Generated
report + process parameter modes; ENG-96505 Element readiness and object attachments mode is not functionally
blocked, but it merges after this ticket (section 4.3).

## 1. The task

### 1.1 Goal

Let `create-business-process` (`parameters[]`) and `modify-business-process` (`addParameter`) declare process
parameters that carry files, so that a Process file element (ENG-92719 File processing element) can take files from
a parameter and pass its file collection on; `describe-business-process` reads them back in a form that rebuilds.

### 1.2 Acceptance criteria as written (Jira, abridged)

| # | AC (abridged) |
|---|---|
| A1 | `addParameter` accepts the "Binary / File" data type; it is "removed from the ProcessParameterService rejection allow-list"; `describe-process` reads it back with its type |
| A2 | A "Binary / File" parameter holds either a single file or a file collection, matching the Files field of the Process file element |
| A3 | It can be mapped into a Process file element's `Files` input, and mapped from its output when `ResultActionType = 1` |
| A4 | Server serialization matches a designer-built capture; tests, docs and MCP surface updated |
