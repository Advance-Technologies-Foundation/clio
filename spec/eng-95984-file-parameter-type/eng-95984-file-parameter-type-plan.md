## 0. Summary

Admit a file as a process parameter **by reference, never by bytes**: `File` is the platform's FileLocator type
(`A33C9252-D401-453E-949D-169157067ED9`, one file) and `FileCollection` is the generic record collection
`CompositeObjectList` (`651ec16f`) with exactly one FileLocator item named `File` (several files). The ticket's
wording does not survive the source: Binary is a Stream type the flow engine cannot store, the platform type NAME
`"File"` resolves to a different BLOB type, one declared type cannot be both a single file and a collection, and the
element outputs exist for both values of `ResultActionType`, not only for 1. Admitting the type is the small half
(about two hours of code). The real work is the binding: the runtime rebuilds a collection's rows from the TARGET's
own items, so a file collection bound only at its outer level saves green and fails at run time (source), while
shipped content binds both levels in 11 of 11 file-collection bindings (measured, corpus). ENG-95984 File process parameter type therefore also
teaches the shared mapping funnel `ProcessMappingService.ApplyMapping` (used by `mappings[]`, `addMapping`, the
mirror, `setConnections` and approvals) to bind both levels and to refuse the shapes
that crash, adds dotted process-parameter paths, and makes describe read back what it wrote. That changes what an
existing operation writes in every process (an item-only multi-instance mapping now also binds its collection), so
the clio `[RequiresPackage]` floor moves and two shipped guidance passages are rewritten under a version gate.
Delivery is one feature PR per repository (CrtProcessBuilder, then clio, then clio-knowledge). Before them comes a
docs-only clio PR with this ticket's BMAD set, which must merge before the package PR leaves draft (section 10). Stand
measurement M3 refuted the suspected ENG-96230 Collection process parameter type mirror defect (H-1) on 2026-10-02,
so no extra triple is added: binding the mirror's items is one parity commit in the package PR. With an AI agent writing the code, it takes about 7.5-15.5 h of agent time and 4.5-10 h of the owner's time; calendar about 3-5 working days from day 0. It blocks ENG-96506 Generated
report + process parameter modes; ENG-96505 Element readiness and object attachments mode is not functionally
blocked, but it merges after this ticket (section 4.3).

## 1. The task

### 1.1 Goal

Let `create-business-process` (`parameters[]`) and `modify-business-process` (`addParameter`) declare process
parameters that carry files, so that a Process file element (ENG-92719 File processing element) can take files from
a parameter and pass its file collection on; `describe-business-process` reads them back in a form that rebuilds.

### 1.2 Acceptance criteria as written (Jira, abridged)

| # | AC (abridged) |
|---|---|
| A1 | `addParameter` accepts the "Binary / File" data type; it is "removed from the ProcessParameterService rejection allow-list"; `describe-process` reads it back with its type |
| A2 | A "Binary / File" parameter holds either a single file or a file collection, matching the Files field of the Process file element |
| A3 | It can be mapped into a Process file element's `Files` input, and mapped from its output when `ResultActionType = 1` |
| A4 | Server serialization matches a designer-built capture; tests, docs and MCP surface updated |

### 3.1 The binder rules in one table

Structured sources only (`sourceElement` + `sourceElementParameter`, or `processParameter`; without `sourceColumn`: a
record column is not a parameter-to-parameter binding). File-consuming targets in this cut: (a) the `Files` input of
ProcessFileProcessingUserTask `6c620dd2-026e-560c-489f-030c5be5f2c3`, recognised by the element's task schema UId (mirrored as `ProcessDesignConstants.FileProcessing`, so a mapping with no file in it
asks the user-task manager nothing), (b) a process-level collection matching the FileCollection predicate. ENG-95985
Send email attachments later adds its attachment slots to this set.

| Rule | Trigger | Writes | Refusal or notice |
|---|---|---|---|
| P1 | target is an item of a collection AND source is an item of a collection | the item, and the target's parents to the source's parents, paired innermost first, as many levels as the SOURCE chain has: a deeper TARGET is fine, only the matching inner levels are bound (`Messages.Files.File` from `OF1.ObjectFiles.File` binds `Messages.Files` and leaves `Messages`); a parent already bound to its source parent, or the same collection, is left as it is | refuse (F-M1) when a paired parent is bound to anything else; refuse (F-M5) when the SOURCE is nested deeper than the target (outside its row it reads empty); the same source is a no-op; type-agnostic, so it applies to `InputRecordCollection.<F>` too; no notice |
| P2 | outer collection mapping onto a file-consuming target that has a FileLocator item | each target FileLocator item not already bound into the new source to the paired source item: exact name (case-insensitive, type-checked), else the single-FileLocator pair (`Files.File` to `ObjectFiles.ObjectFile`); an item that cannot be paired and is bound outside the new source is reset to None; non-file items are never paired | a notice (F-M4) for every item bound, rebound, reset or left unpaired (a rebind and a reset name the old binding; an unpairable item gets "at run time it will be empty"); an item already bound into the new source is neither written nor reported |
| P2-MI | a mapping that binds a multi-instance `InputRecordCollection` (as the named target, or as a parent P1 binds) while one of its FileLocator items stays unbound | nothing extra | notice (F-M4): the callee parameter will be empty on every iteration unless mapped |
| P3 | plain (non-item) source onto a FileLocator item of a single-instance owner (any element but a multi-instance sub-process, or the process itself: a process-level `Docs.File` counts) | the item; EVERY bound collection above it reset to None | one notice (F-M4) per reset level (owner decision: reset, agreed 2026-10-07) |
| R-M1 | flat FileLocator target (a process parameter, or an element input such as a single-instance sub-process's File parameter) from a collection item (`F` from `OF1.ObjectFiles.File`) | - | refuse (F-M2: "use a FileCollection, or a multi-instance sub-process"); M6 (2026-10-02): the mapping reads null, so the refusal stays |
| R-M2 | file-consuming target collection from a collection with no FileLocator item (`Files` from `ReadData.ResultCompositeObjectList`) | - | refuse (F-M3: the source "has no File item") |
| expression | any `expression` source | as given, to the named target only. Since 1.6.6.79 (ENG-102114) the package checks every meta-path token against this process (a misspelled token, a token from another process and a column of a collection item are refused) and stores its GUIDs lower-cased; nested-item tokens such as `Files.File` are accepted | none of the rules above; the platform validates the formula as before |

Every target is resolved and type-checked before the first `SourceValue` write. How PK-PT builds it (draft PR
https://creatio.ghe.com/engineering/crt-process-builder/pull/96, source):
- **Plan, then commit.** `ApplyMapping` plans every write (the named target, P1's parents, P3's resets, P2's items),
  resolving and type-checking each target and running the sub-process direction guard on every planned parent and
  item, and assigns the values only when the whole plan holds: a refused mapping assigns no value (items it walked
  may be adopted: their `ContainerUId` and owning schema are backfilled, as a load of the schema would). Notices are
  recorded after the writes, through `IProcessDesignNotices`, now a constructor dependency of `ProcessMappingService`.
- **One rule source.** The rules are DECIDED in `PB/Mappings/CollectionBindingRules.cs` (static and pure: `Evaluate`
  returns the first refusal, or the P1 bindings, P3 resets and P2 decisions); `ProcessMappingService` turns the plan
  into checks, writes and notices, and describe (D8) asks the same class, so the two sides cannot drift apart.
- **Two explicit entry points.** `BindCollection(schema, outer, itemPairs)` binds both levels: each pair names a
  DIRECT item of either side (matched by name case-insensitively) and is written as given, type-checked, with no
  notice; `null` pairs mean the P2 policy; the outer mapping keeps every other rule, R-M2 and P2-MI included.
  `BindCollectionItems(schema, outer, itemPairs)` binds the pairs only and never writes the outer target, which still
  passes the guards a mapping onto it would (not inside a multi-instance output collection; a sub-process parameter
  must be `In` or `Variable`).

The refusal and notice texts are catalogued as F-T1..F-T7 and F-M1..F-M5 in the decisions document's appendix,
quoted as the code writes them; they are server-side and cost no description bytes.
